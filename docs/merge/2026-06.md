## HTTP 候选的具体边界

### 优先建议：最小行为修复

来源为 `6a41196f`。初评通过静态源码对照定位下列差距；随后 B1 修复前两项，B1b 在讨论反馈策略后完成第三项：

1. **空响应读取保护（B1 已完成）**：旧实现成功回调直接 `const { code } = responseData`，非 2xx 又读取 `(res.data as any).msg`；空体会在 async 回调中抛异常，外层 Promise 仍 pending，finally 无法结束。HTTP 401 空体也会在认证分支前被打断。最终同一测试套件对照旧代码得到 25 项失败，修复后 61 项全过。现实现安全读取业务码，普通 2xx 空 / 非对象响应拒绝原始 `res`，并保留 `original` 和认证优先级。
2. **HTTP 异常提示（B1 已完成）**：非 2xx 现使用解密后 `msg / message`，无业务提示时复用已有 `ShowMessage(statusCode)`；成功码仍保持 0 / 200，拒绝载荷仍为原始 `res`。
3. **网络失败遵守静默参数（B1b 已完成）**：网络 fail 现检查 `hideErrorToast`；同时让 form-create 内置请求默认使用统一 HTTP 提示，显式静默由调用方负责反馈。只加全局网络 guard 会让旧 form-create 路径失去反馈，因此两处行为同批修复。

低风险提取时保持当前 reject 载荷契约；不必为了前述三点同时引入全部 `HttpError` 类型与包装函数。

普通接口的空 / 非对象响应没有已正常工作的失败契约，实施建议统一拒绝原始 `res`，避免 `reject(null)` 或用新造的错误类型扩大契约；正常业务失败继续拒绝原 `responseData`，HTTP / 网络失败继续拒绝原对象。先按 statusCode 进入现有 401 流程，不能用响应结构校验提前截断认证。`original` 继续位于业务码校验之前；验证码原始格式和 `returnRawResponse` 单独纳入回归，不把它们当作普通响应强行归一化。

### 可选：全面统一 HttpError

上游定义 `business / auth / http / network` 四类错误，保留 `code / statusCode / message / data / raw`。便于调用方区分失败来源，但会改变本地现有错误对象形状，属于独立兼容性改动，不能作为纯配置小改直接整段同步。

- 本地业务错误是完整 `responseData`，HTTP / 网络错误仍为原始响应对象。`HttpError` 会把原始字段放进 `raw`，不再保留顶层 `msg / errMsg` 等所有字段。
- 已找到实际调用方：`src/pages-core/auth/components/social-login-panel.vue` 的社交登录 catch 按顶层 `code` 判断未绑定状态，并以顶层 `msg` 显示后端原因。若只套上游包装，`code` 可以保留，`msg` 提示却会退成固定文案。全量迁移前必须盘点并兼容这类调用方，不能只改请求库。
- 上游 `createHttpError` 只是返回普通对象，不是 `Error` 子类；不能据其命名认定 `instanceof Error` 会成立。
- 上游 HTTP README 在本地不存在。若实施统一错误契约，可新写贴合本项目的说明，不复制 alova / vue-query 等本地未采用方案的介绍。
- `isSuccessResultCode` 只是将当前 0 / 200 判断抽成函数，没有新增运行能力；`createHttpError` 也是类型包装，不为追求同形额外抽象。
